# 品質レビューと修正計画

対象: AI Story Builder 2.3.6 / ローカル作業ツリー
調査日: 2026-09-10

## 結論

最優先は、作品データの保存順序と復元の成功判定の修正。既存の型チェック、Lint、800件のテストは通過しているが、Reactの状態更新と非同期保存をまたぐ経路に不整合がある。

初回調査時点では修正を未実施だった。本書は調査結果と実行計画であり、実装状況は末尾に記録する。レビュー専用の一時テストは検証後に削除した。

## 指摘と対応

### Q1 / P1: 保存待ち処理が最新の保存を上書きする

根拠: `src/contexts/ProjectContext.tsx:219,254,647`、`src/hooks/useMemoryLeakPrevention.ts:52`、`src/services/databaseService.ts:270`。

`updateProject`の500ms待機は、既存タイマーを解除しない。更新ごとに古い全量スナップショットを保存予約するため、デバウンスとして機能していない。

再現: 古い更新を予約 → 新しい更新を即時保存 → 500ms経過で古い更新の保存が最後に呼ばれる。画面上は新しい状態のまま。削除後にも予約済みの保存が呼ばれることを確認した。DB側はputによるupsertなので、削除済み作品を再作成する経路にもなる（実DBでの再作成は未検証）。

対応: プロジェクトIDごとの保存窓口を設け、更新世代を管理する。待機保存は最新内容に集約し、即時保存は待機処理を取り消して最新世代の永続化を待つ。削除はそのIDへの新規保存を止め、実行中の保存を整理してから削除する。切替・復元も同じ保存窓口を通す。

完了条件: 手動保存の後に古い内容へ戻らない。削除後に作品が再出現しない。連続入力で変更回数分の全量書き込みが発生しない。fake-indexeddbでも最終保存内容を検証する。

### Q2 / P1: 保留中のAI結果が、その後の編集を巻き戻す

根拠: `src/contexts/ProjectContext.tsx:219`、`src/contexts/PendingResultContext.tsx`、`src/components/tools/CharacterAssistantPanel.tsx:202,213,369,386`。

`updateProject`は作成時のcurrentProjectをマージ元として保持する。保留結果はその関数と既存キャラクター配列を保持するため、反映時点の最新状態を参照しない。

再現: 旧updateProjectを保持 → タイトルを編集 → 保持した関数であらすじを更新すると、タイトルが元へ戻る。保留結果の呼び出し元にも同じ保持パターンを確認した。

対応: 更新対象のprojectIdを明示し、最新状態に対する関数形式の更新を可能にする。AI結果に生成元のID・対象フィールド・基準世代を付与する。反映時に無関係な編集を保持し、対象フィールドの競合は再確認する。別作品への切替や生成元削除時の扱いを明示する。配列追加は反映時点の配列へ適用する。

完了条件: AI生成中の手動編集を保持する。同一tick内の複数更新を失わない。別作品に誤反映しない。削除した作品を保留結果から再作成しない。

### Q3 / P1: 草案Hookがプロジェクト更新時にも古い全量データを書き込む

根拠: `src/components/steps/draft/hooks/useChapterDraft.ts:148,182`。

アンマウント時保存として書かれたeffectがcurrentProjectに依存するため、プロジェクト更新時のcleanupでも保存が走る。そのcleanupは変更前のcurrentProjectを保持している。

再現: Hookのタイトルを変更して再レンダーするだけで、旧タイトルを含む全量保存が呼ばれる。

対応: 草案からDBへの直接全量保存をやめ、Q1の保存窓口へ章IDと本文の変更を渡す。実際の画面離脱・章切替時には最新の未保存本文をflushする。異なる作品・章のスナップショットを混ぜない。

完了条件: 草案以外の編集で旧作品データを保存しない。章切替、ステップ移動、AI反映、入力直後の離脱で本文を失わない。StrictModeでも成立する。

### Q4 / P1: 復元完了前にリカバリーデータを消す

根拠: `src/components/RecoveryDialog.tsx:20,48`、`src/App.tsx:212`。

onRecoverはvoid型で呼ばれ、非同期処理を待たずにclearRecoveryDataとonCloseを実行する。親側も失敗をcatchして通知するだけの経路がある。

再現: onRecoverが未完了のPromiseを返している間に、リカバリーデータが消える。

対応: onRecoverをPromiseベースに変更し、DB永続化成功を待ってから削除する。親から失敗を伝播し、失敗時は復元元とダイアログを保持する。処理中の重複実行も防ぐ。

完了条件: 保存失敗・読み込み失敗時でも同じ復元元で再試行できる。成功時のみ復元元が消える。

### Q5 / P1: 即時保存失敗が成功扱いになる

根拠: `src/contexts/ProjectContext.tsx:232`、`src/components/SearchReplaceModal.tsx:85`、`src/App.tsx:217`。

updateProjectの即時保存経路は例外を通知後に握りつぶす。awaitした呼び出し元は成功扱いで進み、一括置換や復元で成功通知・画面クローズが起き得る。

再現: DB保存を失敗させても、updateProject(..., true)のPromiseは成功で解決する。

対応: Promiseをrejectするか、明示的な保存結果型へ統一する。呼び出し側を全件点検する。未保存・保存中・保存済み・失敗をプロジェクトと編集世代に対応付け、エラー時も未保存内容を保持する。

完了条件: 保存失敗時に成功通知を出さない。再試行可能。古い世代の保存成功で最新編集を保存済みにしない。

### Q6 / P2: 空文字の編集・復元を区別できない

根拠: `src/services/crashRecoveryService.ts:228`、`src/components/steps/draft/hooks/useChapterDraft.ts:98`。

復元のsynopsisと草案保存のcontentで論理ORを使い、空文字を「指定なし」と扱っている。

再現: 空のあらすじを復元しても旧あらすじが残る。草案の空文字引数も同様の実装だが、呼び出し経路による影響は追加確認する。

対応: null/undefinedと空文字を区別し、欠落と意図的削除を保つ。復元データの型・projectId・日時も入口で検証する。

完了条件: 全文削除して保存・復元・再読込しても空のまま。フィールド未収録の場合だけ既存値を維持する。

### Q7 / P2: 自動保存・リカバリー周期が編集ごとに再開始する

根拠: `src/contexts/ProjectContext.tsx:146-217`、`src/services/crashRecoveryService.ts:173`。

自動保存・バックアップ・30秒周期の復元保存をcurrentProject全体に依存したeffectで起動している。頻繁な編集でタイマーが繰り返し停止・開始される。Q1の短時間保存とは別に、周期バックアップが先送りになる構造。

対応: タイマーのライフサイクルを作品ID・必要設定に限定し、内容取得は最新ref経由にする。非同期起動中の停止にも世代チェックを付ける。

完了条件: タイマー間隔より短い周期で編集し続けてもバックアップが実行される。開始・停止競合で重複タイマーが残らない。今回の確認は静的レビュー、周期の再現テストは修正時に追加する。

### Q8 / P2: 読み込み失敗を空の作品一覧と区別できない

根拠: `src/services/databaseService.ts:443`。

getAllProjectsは例外時に空配列を返す。そのためDB障害でも作品0件と解釈される。

対応: エラーを呼び出し元へ返し、一覧の取得失敗・再試行・復元への導線を表示する。既存の一覧状態は不用意に空にしない。

完了条件: DBを失敗させた場合に空状態ではなくエラーを表示する。今回の確認は静的レビュー。

### Q9 / P2: ブラウザ通信の本文受信にタイムアウトが効かない

根拠: `src/services/httpService.ts:158,160,396,398`。

ブラウザ経路ではヘッダー取得後、response.text()の前にタイマーを解除する。本文受信だけ停止すると期限で中断されない。Tauri経路では本文取得後に解除しており、実装が分かれている。

対応: 通信開始から本文読込完了まで期限を保持し、finallyで後始末する。共通部分をまとめ、キャンセルとタイムアウトの扱いを揃える。

完了条件: ヘッダーのみ届いて本文が停止するケースで期限内に失敗する。通常終了後にタイマーが残らない。今回の確認は静的レビュー。

### Q10 / P2: 既存テストがCI・リリースの必須工程にない

根拠: `.github/workflows/release.yml:45`、`.github/workflows/android-build.yml:3`、`vitest.config.ts`。

リリースはLint・型チェックを行うがVitestを実行しない。PR向けAndroidビルドにもVitestがない。既存800件のテストが回帰を自動で止める仕組みに接続されていない。

対応: PR・mainでnpm ci、Lint、型チェック、test:run、フロントエンドbuildを実行する品質ジョブを追加する。リリースにも同じ検証を依存させ、Android側のインストールをnpm ciへ揃える。保存・復元の結合テストを優先する。

完了条件: 意図的に失敗するテストを置いた検証ブランチで品質ジョブが失敗し、リリースジョブが進まない。必須ステータス設定の有無はGitHub設定で別途確認する。

## 実行順序

1. **PR1: 保存エラーと復元の成功判定（Q4・Q5・Q6）**
   - DB失敗時の再試行可能性と、空文字の保持を修正。
   - 完了待ち、失敗保持、重複クリック、成功通知の回帰テストを追加。
2. **PR2: 保存の一元化と草案の競合対策（Q1・Q3・Q7）**
   - プロジェクト別の保存キュー、最新世代管理、削除・切替・復元時の処理を実装。
   - fake-indexeddbで最終内容を確認し、連続入力中の保存・バックアップ回数を検証。
3. **PR3: AI保留結果の安全な適用（Q2）**
   - projectIdと基準世代を持つ変更として適用し、最新状態へマージ。
   - 編集中の生成完了、別作品への切替、生成元削除、競合時の再確認を検証。
4. **PR4: 読み込み・通信の異常系（Q8・Q9）**
   - データ取得失敗と空状態を区別し、本文受信までの期限を保証。
5. **PR5: 継続的な品質保証（Q10）**
   - 既存チェックのCI接続自体はPR1と同時期に着手可能。PR1〜4の回帰テストを順次組み込む。
   - WindowsとAndroidで「作成→編集→保存→再起動→復元→出力」を確認する。

## 後続の保守性改善（P3）

databaseService.tsは2,101行、aiService.tsは2,006行、RelationshipDiagram.tsxは2,309行。行数だけを不具合とはみなさないが、今回の修正と関係する保存・復元・生成適用から責務を分離する。動作保証の回帰テストを先に置き、その後に段階的に分割する。

完了判定はチェック成功だけでなく、「最新の作品内容が再読込後も保持される」「復元失敗で復元元が消えない」「AI結果が無関係な手動編集を巻き戻さない」の3点を必須とする。

ビルドサイズはP3の計測対象とする。初期表示時間・章切替・長編入力の遅延をWindows/Androidで計測してから、重いツール画面の遅延読み込みとimport境界を調整する。現時点ではサイズ警告を確認しただけで、体感速度の劣化は未計測。
